# apü — draft 01

*Status: draft 01, beta toolkit `apue` 0.1.0-beta (2026-10-28), revised after 28 spikes (§15). Sections say whether something is **implemented** (`src/`, tested by `npm test` incl. real browsers and generated Python clients) or a **decision** not to; §13 lists what remains open and why.*
*Research basis: [`research/`](research/) — 01 existing-API problems, 02 HTTP/2 & modern HTTP (+ performance addendum), 03 data plane, 04 Node 26 platform, 05 verified normative details.*

ASCII identifier for media types and header names: **`apue`**.

---

## 1. Goals and non-goals

**Goals**
1. One call model covering unary, server-streaming, client-streaming and bidirectional calls, with one frame format on every transport.
2. Maximum throughput, short TTFB, compression, multiplexing, chunking, streaming.
3. **Fully HTTP/2 compatible** — defined purely in RFC 9110 semantics (methods, status, fields, content). HTTP/2 is used for multiplexing, HPACK and flow control, but nothing depends on h2 framing ⇒ HTTP/3 works unchanged (via an h3-terminating proxy/CDN — Node 26 has no built-in QUIC/HTTP/3, `node:quic` is not available), HTTP/1.1 works for everything except full-duplex request streams (verified, incl. streams over HTTP/1.1 and WebSocket Upgrade).
4. Works from all browsers via `fetch()`, through ordinary CDNs, proxies and load balancers.
5. Fix the top problems of existing styles (see §2).
6. TypeScript-first schemas; language-neutral manifest derived from them.

**Non-goals**
- A query language (GraphQL-style). Field selection is limited and cost-bounded.
- Server-side sessions or sticky connections.
- Relying on trailers, server push, 1xx responses, custom h2 frames/SETTINGS, h2c in browsers, GET with body.

## 2. Problems addressed

## 3. Transport rules

- **MUST** be correct over HTTP/1.1, HTTP/2, HTTP/3. Request streams work over HTTP/1.1 chunked bodies too (tested), but browsers only stream fetch request bodies over h2/h3, and full duplex needs h2/h3 or WebSocket.
- **MUST NOT** depend on trailers, server push, 1xx, priority for correctness, stream IDs, connection affinity.
- Final status of any streamed response **MUST** be carried in-band (END frame, §6).
- Streamed responses **MUST** send `Incremental: ?1` (RFC 10036), `Cache-Control: no-store` (unless cacheable), `X-Accel-Buffering: no`, and commit headers immediately.
- Servers **MUST** send a HEARTBEAT frame if no frame has been sent for 15 s (intermediary timeouts 15–125 s).
- Servers SHOULD limit resources per connection: SETTINGS_MAX_CONCURRENT_STREAMS (apü default 256; Node's own default is unlimited), an idle-session timeout with GOAWAY (default 120 s; heartbeats count as activity), a time limit for unary request bodies (default 30 s → 408) and per-message size limits (413).
- New header fields **MUST** be RFC 9651 Structured Fields with stable names and low-cardinality values (HPACK/QPACK).

## 4. Operations

An operation is identified by a dotted name, e.g. `users.get`, and declares:

| Property | Values | Effect |
|---|---|---|
| `effect` | `safe` · `idempotent` · `unsafe` | HTTP method, cacheability, retry and 0-RTT eligibility |
| `stream` | `none` · `server` · `client` · `bidi` | body framing and transport tier |
| `input` / `output` | schema (`t.*`) | validation (both sides), output stripping, manifest; limits live in the schema (`t.array(x, {max})`, string lengths) |
| `cache` | `maxAge`, `staleWhileRevalidate`, `private` | `Cache-Control` for safe ops |
| `resumable` | boolean | server streams with checkpoints (§8) |
| `deprecated` | `since`, `sunset`, `link` | `Deprecation`/`Sunset`/`Link` headers |
| `description` | text | manifest |

## 5. HTTP mapping

URL: `{base}/{op}` — op name in `:path` (HPACK-friendly, routable, one preflight per op).

| effect | stream | Request |
|---|---|---|
| safe | none/server | `GET {base}/{op}?i={canonical-input}` if the path ≤ 2 KiB, else `QUERY {base}/{op}` with canonical JSON body (Content-Type required, RFC 10008 §2). If QUERY is rejected with 400/403/405/501 (Envoy < 1.40, CloudFront, Akamai) → same request as `POST`; the client remembers this only if POST then fares better. `HEAD` supported wherever GET is. |
| idempotent | none | `POST` + `Idempotency-Key` (client-generated UUID, SF String); retries allowed |
| unsafe | none | `POST` + `Idempotency-Key` (client-generated); retries allowed because of the key |
| any non-safe | client/bidi | `POST`, request stream; never retried (body can't be replayed) |

- `i` = input as **RFC 8785 JCS canonical JSON**, percent-encoded → deterministic cache key.
- **Field selection** (implemented, S9): `?s=a,b.c` on any method (part of the cache key for GET; QUERY/POST carry it in the URL too), `select` per call in batches. Paths are validated against the output schema (unknown → 400 `invalid-selection` before the handler runs), at most 64, through objects, arrays, optional and nullable fields; selecting a parent absorbs children. Applied after output validation, so only schema fields can ever be selected. The ETag covers the projected body. Typed client: `pick(op, input, ['address.city'])` checks paths at compile time and returns `DeepPartial<Output>`. No query language, no joins — cost is bounded by the schema.
- Deadline: `apue-timeout: <ms>` (SF integer; WebSocket: `?timeout=`). The server aborts the handler's signal and answers 504 (`deadline-exceeded`) — also for producers that ignore the signal; client cancellation (AbortController / `break`) resets the stream and aborts the handler.
- Unary response: real HTTP status, `Content-Type: application/json`, errors as `application/problem+json`. (CBOR: decided against, §13.)
- Streaming response/request: `Content-Type: application/vnd.apue.frames` (framed, §6; named `application/apue+json` in earlier drafts — renamed because a `+json` suffix promises a JSON document (RFC 6839 §3.1) and tools such as OpenAPI viewers would try to parse the binary frames), or `text/event-stream` (debug/EventSource rendering). (CBOR: decided against, §13.)
- Reserved paths: `/.well-known/apue` (manifest), `/.well-known/api-catalog` (RFC 9727), `/$batch` (§10). Everything else that is not an op can be served by the application (`fallback`), e.g. the web app itself.
- Safe responses carry a strong `ETag` (SHA-256 of the representation); `If-None-Match` → 304 (weak comparison). `Cache-Control` from the op's `cache` policy, default `no-cache` (revalidate), `private` for caller-dependent ops; non-safe and streams `no-store`. Reads advertise `Accept-Query: "application/json"`.
- Server enforces the mapping: other methods → 405 + `Allow`.
- **Callers** (implemented, S21; research/10): apü defines no authentication — credentials are the standard `Authorization` header (or cookies), checked by the application. Server option `principal(request)` (may be async) names the caller: a stable identity such as a user id, not the credential (which changes on every token refresh), or undefined for anonymous. It scopes idempotency keys, uploads (visibility and quota) and resume tokens, handlers get it as `ctx.principal`, and an error it throws (e.g. 401 with `WWW-Authenticate`) is the response. It runs once per op, batch or upload request (not for the manifest, preflights or `fallback`), before method checks — an unauthenticated call gets its 401 first. Anonymous callers' upload quotas count per address. Without it, scopes are the raw `Authorization` header (a refreshed token is a new scope), resume tokens are bound to op and input only, and upload quotas count per address. Clients: `ApueClient` option `authorization` (a value, or a function asked before every request) — on every tier, including T3 (§8). Proofs of possession (groundwork S25, DPoP S32): the hook also gets the call's `method` and `url` (a WebSocket call is POST, its logical method, so a proof signed for `POST /op` verifies on every tier), the client option `headers({ method, path })` adds per-request headers such as a fresh `DPoP` proof, CORS allows `DPoP` and exposes `WWW-Authenticate`/`DPoP-Nonce`. `dpopVerifier(options)` (apue/server) checks a proof in the hook — every check of RFC 9449 §4.3 (one compact JWS, `typ`, an accepted asymmetric `alg` fitting the key, ≥ 2048-bit RSA, no private key, signature, `htm`, `htu` normalized without query and fragment against `origin` or the request's own, `iat` within 60 s back and 5 s ahead, `ath` with `Authorization: DPoP`), `jti` replays per key (a pluggable atomic store for replicas; recorded only after every other check), optional nonces (401 `use_dpop_nonce`, `DPoP-Nonce` and the problem's `dpop-nonce` member for T3) — and resolves with the key's RFC 7638 thumbprint for the application's `cnf.jkt` binding check (`dpopError('invalid_token', …)`). `createDpopSigner()`/`dpopHeaders()` (apue) sign proofs with WebCrypto (ES256 default, ES384, Ed25519).
- **Idempotency-Key semantics** (draft-08): scope = op + caller (the principal, else hash(Authorization)) + key; fingerprint = SHA-256 of canonical input. Same key + same payload → stored response replayed with `apue-replayed: ?1` (apü extension; the draft defines no header); different payload → 422; original still running → 409 `retryable: true`. Handler 4xx are stored; 5xx and client aborts release the key so a retry re-executes. Stores are pluggable (`idempotency` server option): the contract (`begin`/`complete`/`release`) may return promises, so a store over shared storage serves several replicas — a retry reaching another replica is replayed (S28; the built-in store is per process). A store that fails to record a result doesn't change the response (the operation ran); it is logged. Replays of results with `t.download()` outputs refresh their download URLs, or answer 410 `download-expired` when one is gone (§6).
- **Client retries** (default 2, full-jitter backoff): transport errors, 503/429 (honouring `Retry-After` as delay-seconds or HTTP-date, capped at the max backoff; absent or invalid → backoff), 409 with `retryable: true` — only for safe ops or keyed requests; 504 (deadline) is not retried.
- Input is validated on the client (no request for invalid input) and on the server (400 with `fields`). Output is validated and stripped to the schema (no accidental field leaks); invalid output → 500.

**CORS position:** recommended deployment is same-origin (no preflight). Cross-origin (server option `cors`): allowed origins get `Access-Control-Allow-Origin` (echoed, `Vary: origin`), `Access-Control-Expose-Headers` (etag, apue-replayed, deprecation, sunset, link, retry-after, accept-query, content-encoding) and `Timing-Allow-Origin`; preflights answer 204 with methods `GET, HEAD, POST, QUERY`, only the apü request headers that were asked for, and `Access-Control-Max-Age: 7200` (browser caps: Chromium 7200 s, Firefox 86400 s, WebKit 600 s); disallowed origins' preflights get 403. Credentials require an explicit origin list. apü does **not** accept CORS-simple content types for non-safe ops (CSRF, cf. Apollo GHSA-2p3c-p3qw-69r4) — we pay the preflight rather than open a CSRF hole.

## 6. Framing

Streaming bodies (both directions) are a sequence of frames with an **8-byte header**:

```
 0       1       2       3       4       5       6       7
+-------+-------+-------+-------+-------+-------+-------+-------+
| type  | flags |     lane (u16 BE) |        length (u32 BE)        |
+-------+-------+-------+-------+-------+-------+-------+-------+
| payload (length bytes) ...
```

| type | Name | Payload |
|---|---|---|
| 0x00 | MSG | one encoded message (JSON/CBOR) |
| 0x01 | END | `{status, problem?, meta?}` — terminates a lane. A body that ends while a lane has no END is **truncated** and MUST be treated as an error (detects proxy cut-offs). Lane 0xFFFF reserved |
| 0x02 | BLOB | raw bytes chunk of a binary value of the *next* MSG on the same lane; flag `last` ends that value |
| 0x03 | HEARTBEAT | empty (sent after 15 s without other frames) |
| 0x04 | CHECKPOINT | resume token (§8); SSE rendering: `id:` |
| 0x05 | — | reserved (was: CREDIT for message-level pacing — not specified, see consumer pacing in §8; T3's byte windows use WebSocket text messages) |

Flags: bit0 reserved (was: per-frame compression — not specified: per-stream `Content-Encoding` with a flush per burst already compresses streams without delaying messages, measured TTFB unaffected, §12), bit1 `last` (BLOB), others reserved (MUST be 0). Receivers ignore unknown frame types.

Limits (implemented): a frame header announcing more than the limit is rejected before buffering (request streams: per-message limit = `maxBodyBytes` → 413; malformed → 400; clients map undecodable responses to 502).

- **Lane** = call index in a pipelined batch (§10); 0 for single calls.
- Parser is a byte-stream state machine; DATA-frame / chunk boundaries are meaningless.
- **Binary values** (implemented, S10): schema type `t.bytes()`. For ops whose schema contains bytes, every `Uint8Array` in a message is sent as BLOB frames (64 KiB chunks, last one flagged) *before* the MSG on the same lane; the MSG references them in order as `{"$blob": k}`; look-alike data (sole member `$blob`/`$lit`) is escaped as `{"$lit": value}`. Every blob must be referenced exactly once (else malformed). No base64: measured wire overhead < 1 % for 1 MiB files. Unary ops whose output contains bytes are answered framed (MSG + BLOB + END, not cacheable); bytes in unary *inputs* travel as upload references (next item). Ops without bytes keep the plain `JSON.stringify` fast path and reject BLOB frames. Blobs of one request message count against `maxBodyBytes` (→ 413); request streams use lane 0 only (other lanes → 400). Stored idempotent replays of framed responses decode the stored frames, so bytes come back as bytes.
- **Resumable uploads** (implemented, S18; draft-ietf-httpbis-resumable-upload-14, interop version 10 — research/06): a URL or JSON body cannot carry bytes, and a large upload should survive a lost connection. `POST /$uploads` is a target resource that accepts content (opt-in server option `uploads`); its final response is a reference `{"upload": id, "size": n}`. Op inputs carry `{"$upload": id}` exactly where the schema says `t.bytes()` (schema-directed, so no escaping); the server resolves it before validation, scoped to the caller (§5 Callers; like idempotency keys), 400 with the field path if unknown, incomplete or expired. So unary ops (and batches) can take bytes. The reference's identity for idempotency and resume tokens is the content's SHA-256 (computed as data arrives), not the id: the same bytes uploaded again are the same input. The draft's mechanics as specified: creation with `Upload-Complete`/`Upload-Length`, 104 (Upload Resumption Supported) with `Location` and `Upload-Limit` only for `Upload-Draft-Interop-Version: 10` and only on HTTP/2 (Node's HTTP/1.1 API has no generic 1xx), offset retrieval `HEAD` (`Upload-Offset`, `no-store`), append `PATCH` with `application/partial-upload` (409 + `mismatching-upload-offset` problem on a wrong offset), `DELETE` to cancel, `OPTIONS` discovery, `Upload-Limit: max-size, max-age`, `inconsistent-upload-length` (400). Content is stored as it arrives (an interrupted request keeps what came through); a newer append supersedes one still in flight; limits per upload (413; `max-size` = the smaller of the per-upload and per-client limit, an announced length that can never fit is 413 at creation), per client (bytes received or announced via `Upload-Length` — reserved at creation, so parallel uploads can't overbook — and number of uploads; 507 Insufficient Storage — retrying won't help, deleting will). A client is its principal (§5 Callers); without a `principal` hook it is its address — nothing checks `Authorization` then, so a made-up one must not buy a fresh quota; behind a proxy that is the proxy's address for everyone. Uploads are refused over WebSocket (plain HTTP only) and store-wide (503, retryable); handlers get a copy of the bytes; ids are 128 random bits. The client (`upload()`, and automatically for `t.bytes()` in unary inputs and batches — each distinct buffer once, concurrently) uses the draft's empty "careful" creation (fetch never exposes 104), one `PATCH`, and on loss/5xx/409 `HEAD` + the rest only; creation and offset retrieval are retried within the same budget, honouring `Retry-After`; a failed upload deletes itself; if one upload of a call or batch fails, the others are stopped and awaited, and every completed one is deleted; uploads it made for a call are deleted once the call has settled (`close()` waits for that, each delete time-boxed at 5 s); the reference's id comes from the checked `Location` and must match the final response; `upload()` references are the caller's (`deleteUpload()`); input types accept `UploadRef` wherever the schema has bytes. Idempotency and resume identities use the input with references, not the resolved bytes. Verified in Chrome, Firefox and WebKit cross-origin (preflighted `PATCH`, exposed `Location`/`Upload-*`).
- **File inputs** (spike S20, research/09): schema type `t.file({max?})` for large binary *inputs* — the same upload reference on the wire as `t.bytes()`, but handlers get `{ size, sha256, stream() }` instead of a buffer, and clients may pass a `Blob` (sent and resumed with `slice(offset)`, never read into memory) besides `Uint8Array`/`UploadRef`. Inputs of unary ops only (`op()` rejects it in outputs and request streams). JSON Schema: `contentMediaType: application/octet-stream`, `x-apue-transfer: upload`, `x-apue-max-size`. Server option `uploads.directory` keeps upload content in files (per-process subdirectory, removed on `close()` — or with `uploads.persistent` a fixed, locked directory whose uploads survive restarts, S24; a file is open only while a request writes it or a call reads it — a call opens it at its start, so it stays readable for that call even if the upload is deleted or expires meanwhile; S23), so server memory no longer depends on upload size (measured: peak 223–280 MiB for 128 MiB to 1 GiB uploads, vs the whole upload in memory without it). Limits are validated as positive integers at startup.
- **Download outputs** (implemented, S26; research/11): schema type `t.download({ type? })` for large binary *outputs*, delivered out of band. The handler returns a source `{ size, type?, filename?, sha256?, open(range?) }` (helpers `download.fromFile(path)` — size and mtime taken at once, a file changed later fails the request instead of serving mixed content — and `download.fromBytes(bytes)`, which copies and hashes). The server registers it under an unguessable URL `/$downloads/<128-bit id>` that lives `downloads.ttlMs` (default 15 min) and puts a reference in the output: `{"$download": "/$downloads/…", "size", "type", "sha256"?, "expires"}`. That URL is plain HTTP so links, media elements and download managers can use it: GET/HEAD; one `Range` (206 with `Content-Range`, 416 with `bytes */size`; several ranges or invalid syntax are ignored — 200); `If-Range` against a strong ETag; `If-None-Match` → 304; `Repr-Digest` (RFC 9530) when the digest is known; `Content-Disposition` (RFC 6266, `filename*`) for a filename; `Cache-Control: private, max-age=<remaining>, immutable` (the URL is a capability, like a presigned URL: a link can't carry `Authorization`); CORS exposes the range headers. Bodies are streamed from `open(range)` with backpressure; the first chunk is read before the headers (a failing source is a 500), a failure later resets the stream (never a short 200). Clients turn references into `Download` objects: `url` (absolute when the transport knows its base), `size`, `type`, `sha256`, `expires`, `stream()` (resumes a lost connection with `Range` + `If-Range` within the retry budget; a different representation is an error; verifies the SHA-256 in Node), `bytes()` (verified with WebCrypto everywhere), `blob()`. Outputs only (`op()` rejects them in inputs) and not with a cache `maxAge`/`cdnMaxAge` (the URL would outlive itself in caches). Replicas: the registry is per process like uploads — with the server option `instance` the ids carry the replica's name and load balancers route `/$downloads/<instance>.…` by path (docs/deployment.md, verified through nginx). An Idempotency-Key replay refreshes the expiry of the stored response's download URLs; if one has already expired it answers 410 `download-expired` — never a dead link, never a second run (S28). In-band `t.bytes()` outputs stay for small and medium values: clients accept up to 64 MiB per message and the server holds such an output about three times while answering (value, frames, joined body).
- Why 8 bytes and not Connect's 5: lanes are needed for batches and blobs; 3 extra bytes are noise next to the 9-byte h2 frame header.
- **SSE rendering**: `event: msg|end|checkpoint`, `id: <checkpoint>`, `data: <json>` — same semantics, for curl and devtools; BLOBs as base64 there.

## 7. Errors

- Unary: HTTP status + `application/problem+json` (RFC 9457). Generic errors use `about:blank` with the status phrase as `title`; apü protocol errors have `type` URIs under `https://apue.dev/problems/`, each of which resolves to a page with its members, an example and how clients should react (the website, `site/problems/`): `validation-failed`, `unknown-operation`, `truncated-stream`, `malformed-stream`, `deadline-exceeded`, `idempotency-key-in-progress`, `idempotency-key-reused`, `failed-dependency`, `unresolvable-reference`, `invalid-batch`, `invalid-resume-token`, `invalid-selection`. Extension members: `retryable` (bool), `fields` (per-field validation errors). Unexpected handler errors → 500 without details (logged server-side).
- Streams: if the stream fails before its first item and within the **commit window** (server-chosen, default 50 ms), the server answers with a real HTTP status + problem+json — visible to proxies and dashboards. Otherwise headers are committed (short TTFB) and later failures go into an END frame `{status: <http-status-code>, problem}`.
- Batches: each lane ends with its own END → partial failure is explicit. The HTTP status is 200 if the batch was *accepted*.

## 8. Streaming tiers

| Tier | Client→server | Server→client | Where |
|---|---|---|---|
| T0 | unary body | framed response stream | everywhere (baseline) |
| T1 | framed request stream, full duplex | framed response stream | Node, server↔server (`node:http2`, undici) |
| T2 | framed request stream, half duplex | after upload completes | Chrome only (`duplex: 'half'`) |
| T3 | WebSocket (RFC 6455/8441) carrying the same frames | ← | all browsers |
| T4 | WebTransport bidi stream carrying the same frames | ← | all engines since Safari 26.4; draft |

- Client selection (implemented): Node uses T1 (`http2Transport`); browsers use `autoTransport()` — fetch (T0) for everything, T2 for request streams where fetch can stream uploads, otherwise T3. Whether it can is probed once, on the first request stream (a one-byte streaming POST to the manifest URL, answered 405): the feature detection alone is fooled by WebKit on Linux, which accepts `duplex: 'half'` and then fails every streaming upload (found in CI, S28), and Chrome streams only over HTTP/2. T4 (WebTransport) is blocked by the platform: Node has no WebTransport/HTTP/3 server (§13).
- **Verified in real browsers (S5/S14, headless Chrome 156, Firefox, WebKit 27.2 via Playwright):** T0 everywhere incl. h2, QUERY and preflighted custom headers, compression (zstd) and cancellation; **T2 works in Chrome and in Playwright's WebKit 27.2 build, not in Firefox** (feature-detected; MDN lists release Safari without request streaming — not verified with Safari itself, safaridriver needs sudo); **T3 works in all three**, over RFC 8441 in Firefox and WebKit. T4 not implemented (no WebTransport server in Node).
- **T3 (implemented):** one WebSocket per call with a request stream (`wss://…/{op}`, subprotocol `apue.v1` required; `webSocketTransport` sends calls without a request stream over fetch — a WebSocket has no headers for a unary JSON body or GET input, and would cost a handshake and HTTP caching; found by the leak test, unary over WebSocket had answered 415), carrying the *unchanged* apü frame stream in both directions inside binary messages (message boundaries are irrelevant; fragmentation allowed). Handshake via HTTP/2 extended CONNECT (RFC 8441; the server advertises `SETTINGS_ENABLE_CONNECT_PROTOCOL`) or HTTP/1.1 Upgrade. Observed: Firefox and Node's WebSocket client use RFC 8441 over the existing h2 connection. Chrome (RFC 8441 by default since M91) only *reuses* an existing h2 session with an identical session key and never opens a fresh h2 connection for a WebSocket; a cross-origin fetch without credentials has a different key (privacy mode) than the always-credentialed WebSocket, so Chrome fell back to HTTP/1.1 — with `fetchTransport(url, { credentials: 'include' })` (CORS `credentials: true`) Chrome used RFC 8441 over the shared connection (verified in S6). Same-origin deployment gets this by default. Origin is checked against the CORS list (or same-origin) to prevent cross-site WebSocket hijacking; and since browsers send cookies (and cached HTTP credentials) with every handshake regardless of CORS, a cross-origin handshake keeps `Cookie`/`Authorization` only if CORS allows credentials (explicit list + `credentials: true`) — the rule fetch follows; with `'*'` they are removed (S21). Browsers can't set WebSocket headers, so the deadline is `?timeout=ms` and credentials travel as a second offered subprotocol `apue.auth.<base64url without padding of the Authorization value>` (the Kubernetes pattern): the server selects only `apue.v1` (never echoes the token), gives the call the value as `authorization`, and removes the carrying subprotocol from the headers handlers see; a `DPoP` proof travels the same way as `apue.dpop.<compact JWS>` (token characters already, unencoded) and reaches the call as `dpop`; more than one, a malformed one (not canonical base64url of a valid field value) or one next to an `Authorization` header is answered in-band — the handshake succeeds, nothing runs, the client gets a 400 END frame with the reason (a refused handshake reaches a browser as a bare failed connection; S23). Other headers don't travel over T3 and need not: idempotency keys and resume tokens apply only to calls without a request stream, which go over fetch; errors (including handshake-independent ones like 404/415) arrive in-band as END frames; the client closes with 1000 once it has the END frame (the client core tells the transport via `TransportResponse.complete()`; before END a close is a cancellation, 4000) and the server answers at once — after END the server waits up to 2 s for that before closing with 1000 itself (S17: a server-initiated close right after the last data made WebKit over RFC 8441 drop messages it had not yet dispatched and report 1006, 3–4 in 40 runs of a raw-WebSocket repro, 0 in 40 after the change); the transport ends after both close frames (RFC 6455 §5.5.1, 2 s timeout); 1001 on shutdown; the client closes with 4000 to cancel. Text frames → 1003, unmasked/invalid frames → 1002. `autoTransport()` picks fetch for everything and WebSocket only for request streams when fetch can't stream uploads (Firefox, Safari).
- **T3 flow control (implemented, S17, `apue.v1`):** the browser WebSocket API cannot pause receiving, so without flow control a stalled consumer buffered everything the server produced (measured: 250 MiB in 3 s, RSS +320 MiB; HTTP/2 stopped at its 4 MiB window). Each side grants the other a byte window like HTTP/2 (RFC 9113 §6.9): both start at 64 KiB; binary payload bytes use it up; a **text message** carrying a decimal increment (`"65536"`, 1..2³¹−1, no sign or leading zeros, unfragmented) extends it; a window may not exceed 2³¹−1. Senders split binary data to fit the window exactly. Receivers re-grant what their consumer has taken once that reaches half the window. Violations: invalid/overflowing/fragmented credit, credit inside a fragmented binary message, a continuation without a message, a new message inside one (RFC 6455 §5.4) → 1002 (client: 4002); data beyond the window → 1008 (client: 4008; browsers may only send 1000 and 3000–4999, WHATWG WebSockets §3.1; a handshake response without the requested subprotocol already fails the connection in browsers and undici, §2.2 step 11.2). The server rejects from the frame header, before buffering the payload (a 16 MiB frame announced against a 1 MiB window is refused at once). Windows are configured as integers in [64 KiB, 2³¹−1] (else a startup error). Robustness: a peer that stops reading its socket makes the server stop reading too once 1 MiB of its own pongs/credit is unsent; the browser client additionally waits while more than 4 MiB are unsent (only reachable with server windows above that), polling `bufferedAmount` with a backing-off interval. Why text messages and not an in-band CREDIT frame: credit must never wait behind data the peer has stopped reading (bidi deadlock), and text messages are separable without parsing apü frames, so they bypass the window and both sides can read eagerly — never more than they granted. Defaults: client `receiveWindow` 4 MiB (the client's memory bound per call), server `webSocketWindow` = `streamWindow`, 4 MiB (server memory per call, the same bound as an HTTP/2 request stream; uploads stay below window / RTT — measured at 63 ms RTT through the latency proxy: 1 MiB 6.3 MiB/s, 4 MiB 22.7, HTTP/2 with its 4 MiB window 27.2). Measured: stalled consumer → server stops after 4 MiB (64 × 64 KiB, same as HTTP/2); upload 64 MiB in 1 MiB blobs 285–296 MiB/s locally, without the client's former `bufferedAmount` polling. Through real proxies (docs/intermediaries.md) the credit holds end-to-end (4.0 MiB behind nginx, Caddy, HAProxy, Envoy), while HTTP/2's hop-by-hop windows let the server run 6–7 MiB (nginx, HAProxy), 9.5 MiB (Caddy) and 32 MiB (Envoy) ahead of a stalled consumer (an earlier 125 MiB for Caddy was a probe artifact: compressible items, gzip added by Caddy's upstream transport).
- **Consumer pacing** (decided, research/11): byte-level backpressure bounds *memory* on every tier (HTTP/2 windows, T3 credit, server buffers of 256 KiB), but not how many items a server computes ahead of a slow consumer (a 4 MiB window holds ~85k items of 50 bytes; buffering proxies add 6–32 MiB, browsers 6–15 MiB on fetch). A wire-level demand frame (RSocket REQUEST_N style) was rejected: browsers' server streams use fetch, which has no request stream to carry it, and demand frames queued behind unread request data would reintroduce the bidi deadlock T3 avoids. Patterns instead, which survive any intermediary: (1) *first N* — a `limit`/cursor in the input (cacheable); (2) *N now, more later* — a resumable stream, cancelled after N and resumed with its checkpoint token (any replica); (3) *interactive pacing* — a bidi op where the client sends `{"more": n}` and the handler yields that many (T1, T3). Frame type 0x05 stays reserved.
- **Resume** (implemented, S7): ops declared `resumable: true` (server streams; safe or idempotent only, because resuming re-sends the request). The handler calls `ctx.checkpoint(cursor)` after the items the cursor covers; the server sends a CHECKPOINT frame with a self-contained token `base64url(JSON{op, 128-bit input hash, cursor, expiry}).HMAC-SHA256` (~140 bytes). After a transport loss the client re-sends the call with `apue-resume: <token>` (SSE: `id:` / `Last-Event-ID`); any replica with the shared secret verifies it (no sticky sessions, no stream state) and passes `ctx.resumeFrom`. Invalid, foreign, expired tokens or tokens for another input → 400 `invalid-resume-token` before the stream starts. Contract: from a cursor, the handler replays the same items in the same order; the client counts messages since the last checkpoint and skips that many → exactly-once delivery to the consumer (verified for 30 cut positions × 2 losses). Never resumed: END with an error, malformed frames, no checkpoint yet, budget (`resumes`, default 3) exhausted. Batch lanes and WebSocket calls are not resumable.

### Pattern: long-running operations (no extra protocol needed)

Built only from implemented features (resolves the AIP-151 / MCP-"Tasks" question for apü):

```ts
'reports.start': op({ effect: 'unsafe', input: ReportRequest, output: t.object({ jobId: t.string() }) }),       // POST + Idempotency-Key: retries never start a second job
'reports.watch': op({ effect: 'safe', stream: 'server', resumable: true,                                       // progress events, then the result
                      input: t.object({ jobId: t.string() }), output: JobEvent }),
'reports.get':   op({ effect: 'safe', input: t.object({ jobId: t.string() }), output: JobState }),              // GET, ETag/304: for clients that poll
```

- Start is idempotent through the key, so a lost response is simply retried.
- Watching is a resumable stream: the handler checkpoints after each event (cursor = event sequence
  number); a client that loses the connection resumes on any replica without missing or repeating
  events (exactly-once, §8). The stream ends with the result or an in-band error.
- Polling clients use the cacheable `reports.get`; `If-None-Match` makes unchanged polls cheap.
- Cancellation is an ordinary op (`reports.cancel`, idempotent).

## 9. Caching

- Implemented: `Cache-Control` from the op's `cache` declaration (`max-age`, `stale-while-revalidate`, `private`), strong `ETag` per representation (content-coding and selection included), `If-None-Match` → 304, `Vary` for `accept`, `accept-encoding`, `origin` as applicable, HEAD.
- Implemented (S15): `cache.cdnMaxAge` → `CDN-Cache-Control: max-age=N` (RFC 9213: CDNs use it instead of `Cache-Control`, browsers keep `max-age`); `cache.groups` → `Cache-Groups` and `invalidates` on non-safe ops → `Cache-Group-Invalidation` on successful responses (RFC 9875, SF lists of strings; ≤ 32 groups of ≤ 32 printable ASCII chars, checked in `op()`; only safe ops may declare `cache`, only non-safe ops `invalidates`).
- Decided (S28): no `Location`/`Content-Location` on QUERY responses. Clients use QUERY only when the GET URL would exceed 2048 characters, so a GET-able URL exists only as a server-stored result resource — state for little gain while no CDN caches QUERY (research/05).

## 10. Pipelined batches (promise pipelining)

`QUERY {base}/$batch` (only if every call is `safe`, else 422) or `POST {base}/$batch`, `Content-Type: application/json` (not `/`: that path must stay free for serving the app same-origin; op names start with a letter, so `$batch` can't collide):

```json
{ "calls": [
  { "op": "users.get",   "in": { "id": "42" } },
  { "op": "orders.list", "in": { "userId": { "$ref": [0, "id"] } } },
  { "op": "orders.create", "in": { "item": "x" }, "key": "1f0c…" }
] }
```

- **References**: an object with exactly one member `"$ref": [lane, ...path]` is replaced by the output of an earlier call (path segments: member names or array indices; own properties only; `__proto__`/`constructor`/`prototype` rejected). Data that would look like a reference (exactly one member named `$ref` or `$lit`) is escaped as `{"$lit": value}`; `$lit` content is taken verbatim.
- **Structural validation first** (all-or-nothing `400 invalid-batch`): 1..64 calls (server-configurable), known ops, no request-stream ops, references only to *earlier* calls (⇒ acyclic) and only to unary (`stream: none`) calls, valid `key`.
- **Execution**: each call starts once its dependencies finished; independent calls run concurrently. Inputs are validated after reference resolution (400 `validation-failed`; missing path → 400 `unresolvable-reference`).
- **Response**: always a framed stream, headers committed immediately; each lane delivers `MSG… END` as soon as it completes (out of order) → TTFB = fastest call. Server-streaming ops may be batched (lane carries many MSGs).
- **Failures are per lane**: a failed call ENDs with its problem; dependents END with `424 failed-dependency` (transitively); independent lanes are unaffected. A lane without END when the body ends is truncated (client: 502).
- **Idempotency**: non-safe calls carry a per-call `key` (client-generated), scoped like `Idempotency-Key` → resending the same batch replays keyed calls, so batches are retry-safe as a whole.
- `apue-timeout` applies to the whole batch; cancelling the request aborts all running calls.
- Batching is for **dependencies**; independent calls should just be separate requests multiplexed on h2.
- Client API: `const b = client.batch(); const u = b.call('users.get', {id}); const o = b.call('orders.list', {userId: u.ref('id')}); await b.send(); await o.result` — `ref()` is typed along the output type (up to 3 path segments, through optional fields).
- Decided (S28): no `$map` over arrays. Fanning one call out per element is a remote loop construct with its own limits and failure semantics; an op that takes an array (`users.getMany`) does the same in one call and keeps batches a plain dependency graph.

## 11. Schemas, manifest, evolution

- Schemas are TS objects built from a small erasable-syntax builder with static type inference — no codegen for TS clients.
- `GET {base}/.well-known/apue` → manifest: ops, effects, stream kind, JSON Schema for input/output, cache policy, deprecation, resumability. `ETag` = manifest hash, `no-cache`.
- **Derived documentation** (implemented, S19; research/07–08): generated from the op definitions only — no API change, nothing hand-written, built once at startup (< 1 ms, nothing per request). Size, measured on three APIs: the manifest grows 2.5–3.4× raw (e.g. 1.9 → 5.4 KB), 1.2–1.5 KB gzipped (from 0.3–0.5 KB); it is fetched once by tools and revalidated with ETag/304. (research/08's "+24–32 %" measured the examples alone.). Per op: `http` (methods, path, request/response media types, `idempotencyKey` where honoured), `errors` (the protocol errors beyond the common ones: 408 for JSON bodies, malformed/truncated stream for request streams, 409/422 for keyed ops, invalid resume token), `example` (placeholder input/output — single messages for streams — sampled like Redocly's openapi-sampler, validated with the op's own schema and left out when it doesn't pass, e.g. a regex pattern; bytes inputs as `{"$upload": …}`, none for bytes outputs or void). Top level: `http` (conventions: `?i=`, `?s=`, headers, frames, bytes), `errors` (common protocol errors with RFC 9457 types, `about:blank` when generic), and from the server options `limits` (body size, JSON depth, batch, selection paths, body timeout, heartbeat, uploads). Codegen ignores these fields (verified: byte-identical output, round trip intact); examples are never put inside the JSON Schemas (codegen rejects unknown schema keywords, so older generators would break). A drift test provokes every protocol error kind against every op kind and fails if the server answers with an error the manifest doesn't list for that op. Not derivable without changing `op()` (so not included): errors a handler throws, meaningful example values. 
- `GET|HEAD /.well-known/api-catalog` (RFC 9727, implemented): `application/linkset+json; profile="https://www.rfc-editor.org/info/rfc9727"` with a `service-desc` link to the manifest, and `Link: </.well-known/api-catalog>; rel="api-catalog"` — generic discovery for crawlers and agents.
- **OpenAPI 3.2** (implemented, S28; research/07–08): `GET|HEAD /.well-known/openapi.json` → `application/openapi+json; version=3.2.0` (draft-ietf-httpapi-rest-api-mediatypes; not IANA-registered yet, used de facto), a second `service-desc` in the API catalog, ETag/304, `no-cache`. Derived from the op definitions only (`buildOpenApi`, src/openapi.ts), built on the first request and cached — nothing is spent if nobody asks (todo example: 29 KB raw / 4.2 KB gzipped, 0.3 ms). On by default (it tells nothing the public manifest doesn't); `openapi: false` turns it off, `openapi: { title, version, description, servers }` fills `info`/`servers`. Each op as the server routes it: reads as `get` (input as the `i` query parameter with `content: application/json`), `head`, `query` and `post`; everything else `post`; `Idempotency-Key` where honoured, `apue-timeout`, `apue-resume`, `?s=`, `If-None-Match`/ETag/304. Responses: JSON outputs; framed bodies as opaque binary with the per-message schema as `x-apue-message-schema` (OAS `itemSchema` is only for sequential media types without headers); `text/event-stream` with an `itemSchema` for response streams; RFC 9457 problem responses per status from the protocol errors, a shared `Problem` schema, `default` for handler errors; deprecated ops with their headers; placeholder examples with `dataValue`; upload, blob and download references; `/$uploads`, `/$downloads/{id}` when present. Not described: `/$batch`, the WebSocket tier. Tests validate the documents against the official OAS 3.2 JSON Schemas (vendored with sources and hashes) with a minimal 2020-12 validator; 20 mutations caught.
- **Typed clients without the server's sources** (implemented, S11): `node bin/apue-types.ts <base-url>` turns the manifest into a `defineApi(...)` module with the same `t.*` schemas; verified by a round trip (API → manifest → generated code → identical manifest). The generator rejects JSON Schema keywords it can't express instead of silently dropping constraints. String patterns: JSON Schema `pattern` has no flags, so flags travel as `x-apue-flags` (validators that ignore it see the unflagged pattern — prefer patterns without `i`/`m`/`s` for public APIs); `g` and `y` are refused (they make `RegExp#test` stateful). **Python** (implemented, S27, S29): `--lang python` writes one self-contained module — a standard-library runtime (Python ≥ 3.11, HTTP/1.1 over TLS, keep-alive, one call at a time per client) plus `TypedDict`s, a `Client` with one method per op (`users.get` → `users_get`; keywords and client members get a trailing `_`) and a `Batch` with the same methods. Unary calls (GET `?i=` with canonical JSON in ECMAScript number format, QUERY above 2 KiB with the POST fallback, `Idempotency-Key`, retries on connection loss, 429/503 with `Retry-After` and retryable 409), resumable server streams (`apue-resume`, items since the last checkpoint skipped), client and bidi streams (half duplex: `http.client` sends the whole body before reading, and the standard library has no HTTP/2 or WebSocket client), pipelined batches (`$ref`, `$lit`, per-call keys, QUERY when all calls are safe, lanes with BLOB frames, 424 dependents), compressed responses (zstd on Python ≥ 3.14, gzip; decoded incrementally), client-side input validation against the manifest's JSON Schema in the server's problem shape (UTF-16 lengths; JavaScript patterns translated to `re` — `$`, `.`, `\d \w \s \b` semantics; untranslatable patterns and non-ASCII case-insensitive matching left to the server with a warning), problems incl. END frames, deadlines, bytes in messages, uploads for bytes/file inputs and `t.download()` outputs (Range resume, SHA-256). **Go** (implemented, S29): `--lang go [--package name]` writes one self-contained, gofmt-clean file — a standard-library runtime (Go ≥ 1.24, `net/http`, HTTP/2 over TLS) plus structs with json tags (optional fields as pointer + `omitempty`, slices with `omitzero`; named string types for enums; `[]byte` for bytes; `File` and `Download`) and a `Client` with one method per op taking a `context.Context` (`users.get` → `UsersGet`). Schemas Go can't express are refused, not weakened. Unary calls (the same canonical `?i=` URL as the TypeScript client, POST above 2 KiB, `Idempotency-Key`, retries), server streams (`Recv`/`range` over `All()`, leaving the loop cancels), client and bidi streams **full duplex** over HTTP/2, problems as `*Error` (also from END frames), deadlines and context cancellation, bytes, uploads, downloads (Range resume, SHA-256). Not covered: resuming broken streams, batches, QUERY, compression, client-side validation. **Java** (implemented, S29): `--lang java [--package com.example.api] [--out Api.java]` writes one self-contained Java 17 source file (JDK only, pure ASCII) — records for the types (optional *and* nullable members as `Optional<T>`), enums keeping their JSON names, a thread-safe `Client` over `java.net.http.HttpClient` (HTTP/2, a private CA via `Options.trustedCertificates(pem)`) with unary calls, server streams as `Stream<T>` (closing resets the HTTP/2 stream), client and bidi streams (half duplex: JDK 17's HttpClient exposes a response only after the request body — verified), problems as `ApueException` incl. END frames, deadlines, bytes, uploads (`byte[]`, `Path`, `InputStream`) and downloads (Range resume, SHA-256). Not covered: resuming broken streams, batches, compression, QUERY, client-side validation; enums are strict.
- Evolution: only additive changes within a major; removal via `deprecated` → `Deprecation`/`Sunset` headers.
- Limits are part of the schema (array `max`, string lengths, `t.bytes({max})`) plus server limits (body size, JSON nesting 64, batch size 64, selection ≤ 64 paths) → cost is bounded before a handler runs.

## 12. Data plane & performance guidance

- **Encoding**: JSON (V8-native, debuggable; no replacer/reviver in the hot path); bigint/decimal as strings. CBOR: decided against with measurements (§13, research/11).
- **Compression** (implemented, measured — docs/benchmarks.md): `Accept-Encoding` negotiation (q-values; server preference zstd > br > gzip). Defaults zstd-3, brotli-4, gzip-1 (brotli-11 runs at ~1 MiB/s: never dynamic). Unary bodies ≥ 1 KiB, off the event loop ≥ 64 KiB; `Vary: accept-encoding`; ETag per content-coding. Streams: compressor flushed after every frame burst (TTFB unaffected, tested per coding). On a 100 Mbit/s, 63 ms RTT link zstd gives 2.7× stream and 1.8× bulk throughput. Never mix secrets with attacker-echoed data in one stream. Optional later: RFC 9842 schema-derived dictionary.
- **HTTP/2 tuning (both ends)**: stream window 4 MiB, connection window 32 MiB (Node ≥ 26.11 `connectionWindowSize`; Node 26.12.1 still defaults to 64 KiB, which costs 12× download throughput at 63 ms RTT). The stream window is a throughput/latency trade-off on a shared connection: measured locally, 256 KiB keeps small calls at idle latency next to 900 MiB/s of bulk while 4 MiB adds ~2.5 ms — so it should track the bandwidth-delay product — gRPC-style BDP probing was implemented (`windowTuning: 'bdp'`) but measured no better than a fixed 4 MiB window (docs/benchmarks.md), so 4 MiB stays the default, frames ≤ 16 KiB, TCP_NODELAY, frames coalesced into one write per event-loop turn (≤ 16 KiB), up to 256 KiB buffered per stream before the producer waits for `drain`.
- **Headers**: op in `:path`; few stable SF headers; one entropy field; compact auth tokens.

## 13. Open questions

Resolved:
- `idempotent` ops: POST + key, not PUT (PUT means "replace the target resource").
- QUERY through CDNs: CloudFront (403) and Akamai (501) reject it, nginx/Envoy ≥ 1.40/HAProxy/Fastly forward it, none cache it → client falls back to POST; verified through nginx 1.31.8.
- Browser duplex without request streaming: WebSocket tier T3 instead of correlated request pairs (no shared state needed).
- Compression: per stream via `Content-Encoding` with per-burst flush (measured: TTFB unaffected).
- Projection syntax: dotted paths validated against the output schema.

Open:
1. ~~CBOR~~ → closed with measurements (research/11 §4): codec + validation are ≈ 11 % of server CPU in a unary call (upper bound for any codec); generic CBOR is 0.35–0.94× JSON's encode speed and often larger after compression; only a keyless schema-compiled tuple form wins (≈ 3 % per call) and it breaks evolution and debuggability. Reopen if a real profile shows codec + validation above ~25 %.
2. ~~Resumable uploads~~ → implemented (S18, `/$uploads` + references; client batches upload too). File-backed store and streaming `t.file()` inputs: spike S20. (`server.close()` deadline: S22; uploads surviving a restart: S24; download URLs for very large outputs: S26.)
3. ~~CREDIT frames~~ → not specified: consumer pacing by patterns (§8, research/11); 0x05 reserved.
4. WebTransport (T4) and HTTP/3: **blocked by the platform**, not by the design — checked 2026-10-28: the official Node 26.12.1 build has `node_use_quic: false` (no ngtcp2/nghttp3) and `node:quic` is unknown even with `--experimental-quic`. apü works behind an HTTP/3-terminating proxy (the frames are transport-independent); native T4 follows once Node ships a QUIC server.
5. ~~Problem type namespace~~ → `https://apue.dev/problems/<type>`; every type has a page on the website (generated from `site-src/problems.mjs`, checked against `ProblemType` in src/protocol.ts). The domain is to be registered for the release (it was unregistered on 2026-10-28).
6. ~~Auth~~ → callers (S21, research/10): `principal` hook, credentials over T3 as a subprotocol, no ambient credentials on cross-origin handshakes without CORS credentials. Cross-site cookies (probed in Chrome, Firefox, WebKit): a WebSocket handshake gets exactly the cookies fetch gets. DPoP: groundwork (S25 — method/url for the hook, per-request client headers, `apue.dpop.` on T3), then the profile (S32 — verifier with replay cache and nonces, WebCrypto signer; §5 Callers).
7. ~~Long-running operations~~ → a pattern of start (idempotent) + resumable watch stream + cacheable get (§8).
8. ~~Generators for other languages~~ → TypeScript (S11), Python (S27, S29), Go and Java (S29), Swift (S29; Linux S32). Kotlin users call the Java client.

### S22 — 2026-10-28 ✅ bounded shutdown, idle sessions that GOAWAY can't finish

### S24 — 2026-10-28 ✅ uploads that survive a restart

### S31 — 2026-10-28 ✅ Uploads over emulated networks: two bugs, both on resume

research/09 had left uploads "not measured over a real network". `bench/uploads-wan.ts` (in the bench container, netem on `lo` via `bench/uploads-wan.sh`): a 32 MiB `upload()` into the file-backed store over HTTP/2, then the same upload with its PATCH cut half way (the client resumes on the same connection). The first run never finished the cut case. Two bugs:

1. **ENHANCE_YOUR_CALM after a cut.** The client handed the body to `node:http2` in one 16 MiB write. What was still queued when the stream died kept counting against the client session's memory limit (`maxSessionMemory`, 10 MB by default), so the resumed PATCH — and from then on every new stream on that connection, even HEAD — was refused. Raising the server's limit did not help, the client's did; the fix is in how bodies are written: `pump()` writes in 1 MiB slices with backpressure (`WRITE_SLICE`), and the HTTP/2 transport sends `Uint8Array` bodies above one slice through it. Tests: the cut 32 MiB upload end to end, plus a transport-level test per body kind against a peer that never reads (deterministic: everything beyond the flow-control window stays queued, then the request is aborted). Mutation-checked: without the slicing in `pump` all three fail (3 of 3 runs), without the transport's `Uint8Array` path exactly that test fails (3 of 3).
2. **An outdated offset.** HEAD answered while the cut PATCH's last data was still being appended (16776640, 576 bytes short), so the resumed PATCH got 409 and the client needed another HEAD and PATCH. The draft forbids that (§10: the server "MUST NOT send outdated information"; RECOMMENDED: terminate the previous request before processing a new offset retrieval, append or cancellation). Appends and DELETE already did; offset retrieval now does too (`takeOver`). Test: a hung append, HEAD, late content on the hung stream — the offset stays, the PATCH from it completes, digest correct; fails without the fix (3 of 3). The supersede test, which polled HEAD while its hung append was running, now asserts the draft's allowance instead (409 from the creation's offset, then the final offset is accepted).

**Swift on Linux** (Docker `swift:6.4.1-bookworm`, the version on GitHub's ubuntu-24.04 runners). The runtime did not compile there: `Stream.getBoundStreams` is Apple-only. FoundationNetworking reads a streamed request body without any way to pause (`_BodyStreamSource`: an empty read is the end), on one serial queue shared by every URLSession of the process (`org.swift.URLSession.SharedQueue`), so a body waiting for its next input would stall all networking — measured with a blocking body on a URLSession of its own: a unary call next to a waiting stream took 1.3 s. File bodies would pause, but their length comes from `stat` (0 for a pipe: an empty body). So on Linux request streams collect their inputs and send them when they end (half duplex, at most 64 MiB → 413 before anything is sent). Also: a download cut mid-body surfaces as an unknown error ("HTTP/2 stream not closed cleanly"), so downloads resume on any mid-body URLError (Range + If-Range, SHA-256 verified); there is no CA option on Linux (`URLSessionCertificateAuthorityInfoFile` is Android-only), so the test adds its throwaway certificate to the system store — opt-in `APUE_TEST_SYSTEM_CA=1`, root or passwordless sudo, removed afterwards; CI runs it. The harness checks the portable SHA-256 against Node's digests on both platforms, a call next to a waiting request stream (< 1 s), and the 64 MiB refusal. Mutation-checked on Linux: download resume, the cap, and (before it was replaced) the separate session.
