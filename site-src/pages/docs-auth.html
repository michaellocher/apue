Callers & auth

apü defines no authentication scheme. Credentials are the standard Authorization header or cookies, checked by your application. What apü adds is a single place to name the caller — and the plumbing that makes credentials arrive the same way on every transport.

{{toc}}

The principal hook

The server option principal(request) (may be async) returns a stable identity for the caller — a user or account id, not the credential, which changes on every token refresh — or undefined for anonymous callers. An ApueError it throws, such as a 401 with WWW-Authenticate, is the response.

{{code:docs/auth-server.ts|server.ts}}
  • It runs once per operation, batch or upload request — not for the manifest, preflights or fallback — and before method checks, so an unauthenticated call gets its 401 first.
  • The request it sees has headers, remoteAddress, method and url. A WebSocket call reports POST, its logical method, so a proof signed for POST /op verifies on every tier.
  • The principal scopes idempotency keys, uploads (visibility and quota) and resume tokens. Handlers get it as ctx.principal.

Without the hook these scopes are the raw Authorization header — a refreshed token is a new scope, so a retry after a refresh executes again — resume tokens are bound to operation and input only, and upload quotas count per address (an unverified header must not buy a fresh quota; behind a proxy that address is the proxy’s, for everyone).

Credentials from clients

ApueClient takes authorization — a string, or a function asked before every request — and sends it on every tier: calls, batches, uploads and WebSocket handshakes. The optional headers({ method, path }) hook adds per-request headers.

Credentials over WebSocket

Browsers can’t set headers on a WebSocket handshake, only subprotocols. So on tier T3 the client offers apue.v1 plus apue.auth.<base64url of the Authorization value, without padding> (the pattern Kubernetes uses). The server:

  • selects only apue.v1 — it never echoes the token;
  • hands the value to the call as authorization, and removes the carrying subprotocol from the headers handlers (and their logs) see;
  • accepts a DPoP proof the same way as apue.dpop.<compact JWS>, unencoded, delivered as dpop;
  • answers unusable credentials — more than one, malformed (not canonical base64url of a valid field value), or next to an Authorization header — in-band: the handshake succeeds, nothing runs, and the client gets a 400 END frame with the reason. A refused handshake reaches a browser only as a bare failed connection.

Proxies may log Sec-WebSocket-Protocol like any header, just as they may log Authorization; tokens should be short-lived.

Cross-site WebSocket hijacking

A WebSocket handshake is not subject to CORS, and browsers send cookies (and cached HTTP credentials) with every handshake. apü therefore:

  • checks Origin against the CORS list (or same-origin) before upgrading;
  • lets a cross-origin handshake keep Cookie and Authorization only if CORS allows credentials (an explicit origin list with credentials: true) — exactly the rule fetch follows. With origins: '*' ambient credentials are removed; credentials the page offers explicitly (the subprotocol) still work.

Probed in Chrome, Firefox and WebKit: a cross-site WebSocket handshake gets exactly the cookies a cross-site fetch gets — so the rule matters in every browser.

CORS

The recommended deployment is same-origin: no preflights at all (the server’s fallback can serve the app). For cross-origin browsers, the cors option:

  • echoes allowed origins in Access-Control-Allow-Origin with Vary: origin, exposes etag, apue-replayed, deprecation, sunset, link, retry-after, accept-query and content-encoding (plus the upload, download and auth headers where they apply), and sends Timing-Allow-Origin;
  • answers preflights with 204, methods GET, HEAD, POST, QUERY, only the apü request headers that were asked for, and Access-Control-Max-Age: 7200 by default (browsers cap it: Chromium 7200 s, Firefox 86400 s, WebKit 600 s); disallowed origins get 403;
  • requires an explicit origin list for credentials: true (the server refuses to start otherwise).

apü does not accept CORS-“simple” content types for non-safe operations. A simple request skips the preflight, which is how cross-site request forgery happens (cf. Apollo’s advisory GHSA-2p3c-p3qw-69r4) — apü pays for the preflight instead.

DPoP

DPoP (RFC 9449) binds an access token to a key the client holds: every request carries a fresh proof signed with that key, so a stolen token is useless without it. apü checks proofs on the server and signs them on the client; issuing and validating tokens stays with your authorization server.

Server: dpopVerifier

{{code:docs/auth-dpop-server.ts|server.ts}}

The verifier runs every check of RFC 9449 §4.3: one well-formed compact JWS; typ dpop+jwt; an accepted asymmetric alg (default ES256, ES384, EdDSA/Ed25519, PS256, RS256 with keys of at least 2048 bits) that fits the key; no private key in jwk; the signature; htm equal to the request method; htu equal to the request URI without query and fragment, after normalization; iat at most 60 s old and 5 s ahead; with Authorization: DPoP, ath equal to the token’s hash; and a jti not seen before. It resolves with the key’s thumbprint (jkt, RFC 7638) — compare it with the token’s cnf.jkt — the token, and the claims.

  • Refusals are 401 with WWW-Authenticate: DPoP error="invalid_dpop_proof" and the accepted algs; a request without a proof gets the challenge alone. dpopError('invalid_token', …) builds the same for your binding check.
  • Replays: by default an in-process store remembers each jti while its proof is acceptable. Replicas share one through the replay option — add(key, expiresAt) must be atomic, e.g. Redis SET key 1 NX PXAT expiresAt.
  • Nonces (§9, optional): with nonces: { issue, check } a proof without a valid nonce gets 401 use_dpop_nonce with a fresh one in DPoP-Nonce — and in the problem’s dpop-nonce member, which WebSocket clients can read too. Set signer.nonce and retry.
  • Tiers: a WebSocket call reports POST and its op path, so one proof format verifies everywhere; the proof travels as apue.dpop.<JWS>.

Client: createDpopSigner

{{code:docs/auth-dpop-client.ts|client.ts}}

The signer uses WebCrypto, in browsers and Node: ECDSA P-256 by default, or your own P-256, P-384 or Ed25519 key pair. Each proof gets a random jti, the current iat and, with a token, its ath. CORS allows the DPoP request header and exposes WWW-Authenticate and DPoP-Nonce.
