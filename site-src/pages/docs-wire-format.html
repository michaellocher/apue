Wire format

Unary calls are plain JSON over HTTP. Streaming bodies — in both directions, on every transport — are a sequence of frames with an 8-byte header. This page is the reference for both.

{{toc}}

Frame header

{{pre:text}} 0 1 2 3 4 5 6 7 +-------+-------+-------+-------+-------+-------+-------+-------+ | type | flags | lane (u16 BE) | length (u32 BE) | +-------+-------+-------+-------+-------+-------+-------+-------+ | payload (length bytes) ... {{/pre}}
  • lane: the call’s index in a pipelined batch; 0 for single calls. Lane 0xFFFF is reserved.
  • length: payload bytes. A header announcing more than the limit is rejected before anything is buffered (request streams: maxBodyBytes → 413; malformed → 400; clients map undecodable responses to 502).
  • Parsers are byte-stream state machines: HTTP/2 DATA frame and chunk boundaries mean nothing.
  • Receivers ignore unknown frame types; reserved flag bits must be 0.

Why 8 bytes and not the 5 of gRPC and Connect: the lane is needed for batches and blobs, and three extra bytes are noise next to HTTP/2’s 9-byte frame header.

Messages and binary values

  • Messages are JSON. Operations without bytes use the plain JSON.stringify fast path.
  • For operations whose schema contains t.bytes(), each Uint8Array becomes BLOB frames (64 KiB chunks, last one flagged) before the MSG on the same lane, which references them in order as {"$blob": k}. Look-alike data is escaped as {"$lit": value}; every blob is referenced exactly once.
  • Upload references in inputs: {"$upload": "<id>"}. Download references in outputs: {"$download": "/$downloads/<id>", "size", "type", "sha256"?, "expires"}. See Binary data.
  • Batch references: {"$ref": [lane, ...path]}, escaped with $lit as well.

Resume tokens

base64url(JSON{op, 128-bit input hash, cursor, expiry}) + "." + HMAC-SHA256, about 140 bytes. Clients send it back as apue-resume: <token>; in the SSE rendering it is the event id: and comes back as Last-Event-ID.

SSE rendering

With Accept: text/event-stream, a response stream is rendered as server-sent events with the same semantics — for curl, devtools and EventSource:

  • event: msg / event: end / event: checkpoint, each with data: <json>;
  • checkpoints as id: <token>, so a reconnecting EventSource resumes with Last-Event-ID;
  • BLOBs as base64 (the only place apü uses base64).
{{pre:console|from docs/wire.md}} $ curl -N -H 'accept: text/event-stream' https://localhost:18443/todos.changes event: msg data: {"seq":0,"todo":{"id":1,"title":"buy milk","done":false}} id: eyJvIjoidG9kb3MuY2hhbmdlcyIsImgiOiJkQ05PbUtfblNZLTEydkh6YXNMWGlzIiwiYyI6IjAiLCJlIjoxNzkzMTU3MTYyfQ.eAZG95XzOEl3G_X9rO8ti6IU_-j-2CGfowiVdn8t1Sg {{/pre}}

WebSocket tier (T3)

AspectRule
URL and handshakewss://<host>/<op>?timeout=<ms>; RFC 8441 extended CONNECT over HTTP/2 (the server advertises SETTINGS_ENABLE_CONNECT_PROTOCOL) or HTTP/1.1 Upgrade
Subprotocolsapue.v1 required; optional apue.auth.<base64url> and apue.dpop.<JWS>; the server selects only apue.v1
Binary messagesThe unchanged apü frame stream; message boundaries are irrelevant, fragmentation allowed
Text messagesFlow-control credit: a decimal increment in 1..2³¹−1, no sign or leading zeros, unfragmented. Both windows start at 64 KiB.
Normal endThe client closes with 1000 after the END frame; after END the server waits up to 2 s, then closes with 1000 itself
Cancellation, shutdownClient 4000 (before END); server 1001 on shutdown
ViolationsUnmasked or invalid frames, invalid or overflowing credit, credit inside a fragmented binary message → 1002 (client: 4002); data beyond the window → 1008 (client: 4008). Browsers may only send 1000 and 3000–4999, hence the client codes.

Unary calls never use the WebSocket tier: idempotency keys and resume tokens therefore only ever travel as HTTP headers.
