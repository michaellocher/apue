Pipelined batches

Dependent calls normally cost one round trip each. A batch sends them together; a later call can reference an earlier call’s output, and the server resolves the reference itself — promise pipelining over plain HTTP.

On this page

  • From the client
  • On the wire
  • What it saves
  • Limits and plans

From the client

ref() is typed along the output type (up to three path segments, through optional fields), so todo.ref('id') can stand wherever a number is expected. batch.stream(op, input) adds a server-streaming lane whose items you iterate. send() resolves when every lane has ended and rejects only if the batch as a whole fails.

Batching is for dependencies. Independent calls should just be separate requests: HTTP/2 multiplexes them on one connection.

On the wire

POST {base}/$batch — or QUERY, if every call is safe (else 422) — with a JSON body. (Not /: that path stays free for serving the app itself.)

  • References: an object whose only member is "$ref": [lane, ...path] is replaced by the output of an earlier call (path segments are member names or array indices; own properties only; __proto__, constructor and prototype are rejected). Data that would look like a reference is escaped as {"$lit": value}.
  • Structural validation first, all or nothing (400 invalid-batch): 1 to 64 calls (maxBatchCalls), known operations, no request-stream operations, references only to earlier unary calls — so the graph is acyclic — and valid keys.
  • Execution: each call starts once its dependencies have finished; independent calls run concurrently. Inputs are validated after references are resolved (400 validation-failed; a missing path: 400 unresolvable-reference).
  • Response: always a framed stream with headers committed at once. Each lane delivers MSG… END as soon as it completes, in any order, so the first result arrives as soon as the fastest call is done. Server-streaming operations may be batched; their lane carries many MSG frames.
  • Failures are per lane: a failed call ends its lane with its problem; dependents end with 424 failed-dependency, transitively; independent lanes are unaffected. A lane without END when the body ends is truncated (502 on the client).
  • Idempotency: non-safe calls carry a per-call key, scoped like Idempotency-Key — resending the same batch replays the keyed calls, so a batch is retry-safe as a whole.
  • apue-timeout applies to the whole batch; cancelling the request aborts every running call. Batch lanes are not resumable.

A real batch response

Create a todo and complete it in one round trip (from docs/wire.md). Lane 0 is the create, lane 1 the complete that referenced lane 0’s id:

00 00 0000 00000024MSG036{"id":2,"title":"ship","done":false}
01 00 0000 0000000eEND014{"status":200}
00 00 0001 00000023MSG135{"id":2,"title":"ship","done":true}
01 00 0001 0000000eEND114{"status":200}

What it saves

Measured for three dependent calls (Node 26.12.1, TLS + HTTP/2): locally 0.67 ms sequential vs 0.31 ms as a batch; in a 1-CPU Docker container behind an emulated WAN link (63 ms RTT, 100 Mbit/s) 203 ms vs 67 ms (3.0×). On real networks the round trips dominate. Details on the Measurements page.

Limits and plans

  • Request-stream operations (client, bidi) can’t be batched.
  • The generated Python client does not support batches.
  • planned $map over arrays (in the style of Cap’n Web).

apü

An API protocol built on plain HTTP semantics. Research draft 01, October 2026 — not a stable standard, and no package is published yet.

The name is written apü; URLs, headers and media types use apue.
