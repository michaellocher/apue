Binary data

JSON can’t carry bytes without base64, a URL can’t carry them at all, and a large transfer should survive a lost connection. apü has three schema types for binary values, from small to very large.

BLOB frames

For operations whose schema contains bytes, every Uint8Array in a message is sent as BLOB frames — 64 KiB chunks, the last one flagged — before the MSG frame on the same lane. The MSG references them in order as {"$blob": k}. JSON that merely looks like such a reference (an object whose sole member is $blob or $lit) is escaped as {"$lit": value}. Every blob must be referenced exactly once. Measured wire overhead: under 1 % for 1 MiB files.

  • Unary operations whose output contains bytes are answered framed (MSG + BLOB + END) and are not cacheable.
  • Operations without bytes keep the plain JSON.stringify fast path and reject BLOB frames.
  • The blobs of one request message count against maxBodyBytes (413); request streams use lane 0 only.
  • A t.bytes() output is held in memory — about three times on the server while answering — so very large outputs belong in t.download().

Resumable uploads

Bytes in unary inputs are uploaded first, then referenced. POST /$uploads follows draft-ietf-httpbis-resumable-upload-14 (interop version 10) — an IETF draft, not yet an RFC. Its final response is a reference {"upload": id, "size": n}; operation inputs then carry {"$upload": id} exactly where the schema says t.bytes() or t.file(). The server resolves the reference before validation, scoped to the caller; an unknown, incomplete or expired one is a 400 naming the field.

Uploads are off by default (they are storage any client can fill) and required by operations with bytes in a unary input: the server refuses to start without the uploads option for such an API.

Protocol, as implemented

  • Creation with Upload-Complete / Upload-Length; 104 Upload Resumption Supported with Location and Upload-Limit only for interop version 10 and only on HTTP/2 (Node’s HTTP/1.1 API can’t send generic 1xx responses).
  • Offset retrieval with HEAD (Upload-Offset), appending with PATCH and application/partial-upload (409 mismatching-upload-offset on a wrong offset), DELETE to cancel, OPTIONS discovery, Upload-Limit: max-size, max-age.
  • Content is stored as it arrives, so an interrupted request keeps what came through; a newer append supersedes one still in flight.
  • Limits per upload (413; an announced length that can never fit is refused at creation) and per client (bytes and number of uploads, announced lengths reserved at creation; 507). A client is its principal, else its address.
  • The identity of a referenced upload for idempotency and resume tokens is the content’s SHA-256, computed as data arrives — the same bytes uploaded again are the same input.
  • Uploads go over plain HTTP only, never over WebSocket. Upload ids are 128 random bits.

The client

The client uploads automatically for t.bytes()/t.file() in unary inputs and batches — each distinct buffer once, concurrently — using the draft’s empty “careful” creation (fetch never exposes 104), one PATCH, and after a loss, 5xx or 409 a HEAD plus only the rest. Uploads made for a call are deleted once the call has settled; if one upload of a call fails, the others are stopped and deleted. client.upload() returns a reference that stays yours until deleteUpload() or expiry. A Blob is sent and resumed with slice(offset), never read into memory. Verified cross-origin in Chrome, Firefox and WebKit.

File inputs and the file-backed store

t.file() uses the same upload reference as t.bytes(), but the handler gets { size, sha256, stream() } instead of a buffer. With uploads.directory the server keeps upload content in files, so its memory no longer depends on upload size:

  • Measured with 512 MiB through a separate server process: 380–463 MiB/s with a server peak RSS of 255–267 MiB, constant from 128 MiB to 1 GiB uploads — versus the whole upload in memory without a directory.
  • A call opens its file inputs when it starts, so they stay readable for that call even if the upload is deleted or expires meanwhile; descriptors are open only while a request writes or a call reads.
  • uploads.persistent keeps uploads across restarts in <directory>/apue-uploads (one process per directory, guarded by a lock file). On startup each file is cut back to its last recorded length — content is never corrupt; clients resend what was never acknowledged.

Not covered: several replicas sharing uploads (a resumed request must reach the instance holding the upload) and several hosts on one network directory.

Downloads

A t.download() handler returns a source — { size, type?, filename?, sha256?, open(range?) } — or uses the helpers download.fromFile(path) (size and modification time are taken at once; a file changed later fails the request rather than serving mixed content) and download.fromBytes(bytes) (copies and hashes). The server registers it under an unguessable URL /$downloads/<128-bit id> for downloads.ttlMs (default 15 minutes) and puts a reference in the output:

That URL is plain HTTP, usable by links, media elements and download managers:

  • GET and HEAD; one Range (206 with Content-Range, 416 with bytes */size; several ranges or invalid syntax are ignored → 200); If-Range against a strong ETag; If-None-Match → 304.
  • Repr-Digest (RFC 9530) when the digest is known; Content-Disposition (RFC 6266, filename*) for a filename.
  • Cache-Control: private, max-age=<remaining>, immutable — the URL is a capability, like a presigned URL, because a link can’t carry Authorization. CORS exposes the range headers.
  • Bodies stream from open(range) with backpressure. The first chunk is read before the headers (a failing source is a 500); a failure later resets the stream — never a short 200.

Clients turn references into Download objects with url, size, type, sha256, expires and stream() (resumes with Range + If-Range within the retry budget; a changed representation is an error; verifies the SHA-256 in Node), bytes() (verified with WebCrypto everywhere) and blob().

Not covered: replicas (the registry is per process, like uploads); an idempotent replay returns the stored reference, whose URL may have expired.

apü

An API protocol built on plain HTTP semantics. Research draft 01, October 2026 — not a stable standard, and no package is published yet.

The name is written apü; URLs, headers and media types use apue.
