Measurements

Numbers from the repository’s benchmark reports, with the conditions they were measured under. They describe the Node reference implementation on these machines, not protocols in general.

Setup

  • Node 26.12.1, TLS + HTTP/2, JSON payloads, measured 2026-10-28.
  • node bench/run.ts: server and client in separate processes on one machine (M-series, 10 cores, 16 GiB).
  • bench/docker.sh: server in a CPU/RAM-limited container, client in a second container sharing its network namespace; optional tc netem latency and bandwidth limit. “WAN” = 25 ms delay each way, 100 Mbit/s; ping measured 63 ms RTT.
  • Baselines are hand-written node:http2 endpoints without validation, framing or features: a minimal JSON GET, NDJSON for streams (written without backpressure), a plain JSON response for bulk. They are a ceiling, not a competitor; the gap is the cost of schema validation and stripping, ETags, idempotency keys, framing, deadlines and cancellation.
  • “c=32” = 32 concurrent calls on one HTTP/2 connection.

Against gRPC

@grpc/grpc-js 1.14.6, the official Node implementation. Same machine and shapes (the protobuf mirrors the benchmark API), TLS + HTTP/2 for both, servers and client in separate processes. apü validates and strips every output against its schema; gRPC does schema encoding instead.

The stream gap is grpc-js’ per-message cost, not the harness: with and without server backpressure, and with for await or 'data' events on the client, grpc-js stayed at 56–59k msg/s. apü’s frame coalescing, batched decoding and single-allocation encoding make the difference. This says nothing about gRPC in Go, C++ or Rust.

Time to first byte

20 rows produced 10 ms apart, loopback: a buffered unary response arrives after 219.6 ms (fetch) / 220.3 ms (http2); as an apü stream the first row arrives after 12.0 ms / 11.7 ms, the whole stream after about the same 220 ms.

256 KiB0.36 / 11.48 ms0.21 / 1.46 ms899 MiB/s
  • A small window keeps small calls at idle latency next to bulk — on loopback. On a WAN the window must be at least the bandwidth-delay product (63 ms × 100 Mbit/s ≈ 790 KB) or throughput collapses (12× in the WAN profile). apü’s 4 MiB default favours WAN throughput; latency-sensitive LAN deployments can choose a smaller fixed window.
  • gRPC-style BDP window auto-tuning was implemented (windowTuning: 'bdp') and measured no better than a fixed 4 MiB window (2 × 16 MiB downloads at 40 ms RTT: 20.8 vs 41.8 MiB/s), so it is opt-in.
  • The 11–15 ms p99 next to JSON downloads is JSON.parse/stringify of 8 MiB values, independent of the window: large data belongs in t.bytes() or in streams of smaller messages.

Uploads and the WebSocket tier

  • 64 MiB as a unary t.bytes() input (resumable upload, SHA-256 as data arrives): 474–503 MiB/s locally, vs 446–468 MiB/s as BLOB frames in a client stream.
  • 512 MiB t.file() uploads to a file-backed store: 380–463 MiB/s at a server peak RSS of 255–267 MiB, constant from 128 MiB to 1 GiB.
  • WebSocket (T3) uploads, 64 MiB in 1 MiB blobs, locally: 285–296 MiB/s with flow control; a 100k-message client stream over WebSocket 972k msg/s (HTTP/2: 905k).
  • Uploads at 63 ms RTT through a latency proxy: 6.3 MiB/s with a 1 MiB WebSocket window, 22.7 MiB/s with 4 MiB (HTTP/2 with its 4 MiB window: 27.2).

Through proxies

With a consumer that stalls while the server produces 64 KiB items as fast as allowed: directly, HTTP/2 flow control stops the server at the client’s 4 MiB window. Through proxies each hop has its own window and buffers — the server got 5.8–7.0 MiB ahead through nginx and HAProxy, 9.5 MiB through Caddy and 32 MiB through Envoy. The WebSocket tier’s end-to-end credit stopped it at exactly 4.0 MiB behind every proxy that passes WebSockets. Full results on Caching, CDNs & proxies.

Conclusions from the report

  1. On real networks the protocol design dominates, not CPU: at 63 ms RTT the unary overhead disappears (95 % of a raw handler), while batches (3.0×), compressed streams (2.7×) and tuned flow-control windows (5–12×) decide throughput and latency.
  2. The HTTP/2 window defaults are a trap: Node 26.12.1 still advertises the RFC’s 64 KiB; apü sets 4 MiB per stream and 32 MiB per connection on both ends.
  3. zstd is the right default: zstd-3 reaches about brotli-4’s ratio (118 vs 101 KiB for 1 MiB) at about 1.5–1.7× its speed. On loopback compression costs throughput; behind 100 Mbit/s it is a net win.
  4. The remaining cost is CPU against a hand-written handler: 47–64 % of its throughput for tiny unary calls and 48–75 % for message streams — a handler that does no validation, no ETags, no idempotency and no backpressure.

Caveats

  • Docker Desktop runs containers in a VM on the same Mac; “1 CPU” is a CFS quota, which causes tail latencies (p99 50–66 ms at 0.5 CPU). At 0.5 CPU, bulk numbers swing ±20 % between runs: that cell shows noise, not a difference.
  • WAN runs vary: the tuned-window download was 7.0 MiB/s in one run and 2.9 MiB/s in the final one.
  • netem applies to both directions of the shared loopback interface.
  • Clients ran unconstrained; constrained clients would be slower.
