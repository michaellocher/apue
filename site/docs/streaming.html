Streaming

One call model covers unary, server-streaming, client-streaming and bidirectional calls, with one frame format on every transport. What changes between Node and the browsers is only which transport carries it.

Stream kinds

An operation’s stream decides the handler’s shape: for client and bidi the input is an AsyncIterable of messages; for server and bidi the handler returns an AsyncIterable (an async generator is the easy way).

Streamed bodies are frames with an 8-byte header (application/apue+json, see the wire format). A response stream ends with an END frame carrying the final status; a body that ends without one is truncated and treated as an error — that is how proxy cut-offs are detected.

Client selection: Node uses T1 (http2Transport). Browsers use autoTransport(): fetch (T0) for everything, T2 for request streams where fetch can stream uploads, otherwise T3. Verified in real browsers (headless Chrome, Firefox, and Playwright’s WebKit 27.2): T0 everywhere including HTTP/2, QUERY, preflighted custom headers, zstd and cancellation; T2 in Chrome and that WebKit build, not in Firefox (feature-detected); T3 in all three, over RFC 8441 in Firefox and WebKit. Release Safari itself was not automated.

HTTP/1.1 works for everything except full-duplex request streams: request streams over HTTP/1.1 chunked bodies were tested, but browsers stream fetch request bodies only over HTTP/2 and HTTP/3. HTTP/3 should work unchanged behind an HTTP/3-terminating proxy or CDN, since nothing depends on HTTP/2 framing — untested, because Node 26 has no QUIC of its own.

Heartbeats, commit window, headers

  • Headers immediately. Streamed responses send Incremental: ?1 (RFC 10036), Cache-Control: no-store and X-Accel-Buffering: no and commit their headers at once — measured: first item after 12.0 ms vs 219.6 ms for the same data as one buffered response (20 rows × 10 ms, loopback).
  • Commit window. If a stream fails before its first item and within the commit window (default 50 ms, commitAfterMs), the response is a real HTTP status with problem details, visible to proxies and dashboards. Later failures go into the END frame.
  • Heartbeats. After 15 s without another frame the server sends a HEARTBEAT frame, because intermediaries time out idle responses after 15–125 s.
  • Compression (zstd, brotli, gzip by Accept-Encoding) is per stream and flushed after every burst of frames, so it doesn’t delay the first byte.
  • SSE view. With Accept: text/event-stream the same stream is rendered as server-sent events — event: msg|end|checkpoint, data: JSON, checkpoints as id: — for curl and devtools.

Resumable streams

Operations declared resumable: true (server streams; safe or idempotent) survive a lost connection without sticky sessions or server-side stream state:

  1. The handler calls ctx.checkpoint(cursor) after the items the cursor covers. The server sends a CHECKPOINT frame with a self-contained token: base64url(JSON{op, 128-bit input hash, cursor, expiry}).HMAC-SHA256, about 140 bytes.
  2. After a transport loss the client re-sends the call with apue-resume: <token> (SSE clients: Last-Event-ID). Any replica holding the shared secret (resume.secret) verifies it and passes the cursor to the handler as ctx.resumeFrom.
  3. The handler replays from that cursor; the client counts messages since the last checkpoint and skips that many, so the consumer sees every item exactly once (tested for 30 cut positions × 2 losses).

The contract for the handler: from a cursor, yield the same items in the same order as the original stream did after that checkpoint. Invalid, foreign or expired tokens, and tokens for another input, are 400 invalid-resume-token before the stream starts. With a principal hook, tokens are bound to the caller. Tokens live 15 minutes by default (resume.ttlMs).

Never resumed: an END frame with an error, malformed frames, a loss before the first checkpoint, an exhausted budget (resumes, default 3). Batch lanes and WebSocket calls are not resumable.

The WebSocket tier (T3)

Browsers can’t stream request bodies everywhere, so request streams use one WebSocket per call to wss://…/{op} with the subprotocol apue.v1. Binary messages carry the unchanged apü frame stream in both directions; message boundaries don’t matter. The handshake uses HTTP/2 extended CONNECT (RFC 8441) when available, else HTTP/1.1 Upgrade. Calls without a request stream never use T3 — a WebSocket would cost a handshake and HTTP caching.

  • Browsers can’t set WebSocket headers: the deadline travels as ?timeout=ms and credentials as an extra subprotocol (Callers & auth). Errors, including 404 and 415, arrive in-band as END frames.
  • The client closes with 1000 once it has the END frame; a close before END is a cancellation (4000). After END the server waits up to 2 s for that close before closing itself — closing right after the last data made WebKit over RFC 8441 drop messages.
  • Flow control. The browser WebSocket API can’t pause receiving: without flow control a stalled consumer let the server push 250 MiB into page memory in 3 s. So each side grants the other an HTTP/2-style byte window: both start at 64 KiB, binary payload bytes use it up, and a text message with a decimal increment (e.g. "65536") extends it. Receivers re-grant what their consumer has taken once it reaches half the window. Defaults: client receiveWindow 4 MiB, server webSocketWindow = streamWindow, 4 MiB. Measured: a stalled consumer stops the server after exactly 4 MiB, also behind nginx, Caddy, HAProxy and Envoy.

Chrome reuses an existing HTTP/2 connection for a WebSocket only if the session key matches; a cross-origin fetch without credentials has a different key, so Chrome falls back to HTTP/1.1 for the WebSocket. fetchTransport(url, { credentials: 'include' }) with CORS credentials let Chrome use RFC 8441 over the shared connection. Same-origin deployments get this by default.

Backpressure and consumer pacing

Byte-level backpressure bounds memory on every tier: HTTP/2 windows, T3 credit, and at most 256 KiB buffered per stream on the server before the producer waits. It does not bound how many items a server computes ahead of a slow consumer: a 4 MiB window holds about 85,000 items of 50 bytes, buffering proxies add 6–32 MiB, browsers 6–15 MiB on fetch.

A wire-level demand frame (RSocket REQUEST_N style) was considered and rejected: browser server streams use fetch, which has no request stream to carry demand, and demand frames queued behind unread request data would reintroduce a bidi deadlock. Frame type 0x05 stays reserved. Use patterns instead, which work through any intermediary:

  1. First N — a limit or cursor in the input (cacheable).
  2. N now, more later — a resumable stream, cancelled after N and resumed later with its checkpoint token, on any replica.
  3. Interactive pacing — a bidi operation where the client sends {"more": n} and the handler yields that many (tiers T1 and T3), like feed.paced above.

Pattern: long-running operations

No extra protocol is needed; the pattern is built from implemented features:

  • Starting is idempotent through the key: a lost response is simply retried and never starts a second job.
  • Watching is a resumable stream: the handler checkpoints after each event (cursor = event sequence number), so a client that loses its connection resumes on any replica without missing or repeating events. The stream ends with the result or an in-band error.
  • Polling clients use the cacheable reports.get; If-None-Match makes unchanged polls cheap. Cancelling is an ordinary idempotent operation.

Graceful shutdown

server.close() lets calls in flight finish for shutdownGraceMs (default 10 s), then ends the rest with a retryable 503 — as the response, or as an END frame for streams already running — so clients retry or resume elsewhere; remaining connections are dropped. Before this bound existed, close() never returned while a client consumed an endless server stream. Idle HTTP/2 sessions are closed with GOAWAY after idleTimeoutMs (120 s) and destroyed if still idle one period later.
